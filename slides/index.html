Part 1 · What is it

System One models: fast, structured decisions

Definition. A System One model is a class of AI models built to make fast, structured decisions that software can use directly. It evaluates a state and returns typed answers and probabilities. Jev is TypeSafe's flagship and the first System One model.
flowchart LR
  input["state + questions"]
  subgraph model["Jev"]
    evaluate["evaluate each question
against the state in parallel"]
  end
  input -- "one request" --> model
  model -- "one response" --> answers["typed answers
+ probabilities + confidence"]
  answers --> code["your code
branch · sort · route"]

It does

Understand natural language and return a typed decision plus probabilities.

It does not

Write replies, produce code, or explain its reasoning.

Why "System One"?

Kahneman's Thinking, Fast and Slow: fast, intuitive judgment.

Source: /concepts/system-one · /introduction
  • Input today is text only: strings, JSON objects, arrays of text. No images, audio or video (yet).
  • Think "gut-check a knowledgeable person makes in a few seconds, given the right context".
  • All questions in one request run in parallel and cannot see each other's answers.

Part 1 · What is it

Trained for calibrated decisions (RLCD)

RLHF

Human feedback. Made chatbots: answers people prefer.

RLVR

Verifiable rewards. Made reasoning models: strong, but slower and costlier.

RLCD

Reinforcement learning for calibrated decisions: returns decisions and probabilities, not text.

Calibrated = among all predictions where the model assigns probability 0.8 to its answer, about 80% are correct. Same for 0.2 → ~20%, 0.95 → ~95%.
  • Example: 1,000 tickets where probabilities["technical"] = 0.80 → about 800 are really technical.
  • Overconfident model: says 0.99 but is right 70% of the time. Its probabilities cannot be used as thresholds.
  • About the probabilities (not confidence), and about groups of predictions, not one answer. Validate on your own data.
Source: /introduction/machine-learning-primer · /concepts/system-one
  • RLCD is TypeSafe's term. The docs describe it only at a high level: probabilities "optimized against outcomes to reflect uncertainty". No reward function or paper is published in the docs.
  • Their critique of RLHF: rewards what people prefer, which can reward sycophancy and confident-sounding hallucinations; "mode dropping". Human preference is not machine trustworthiness.
  • Why it matters: calibration is what lets a threshold like "act above 0.85, else ask a human" have a predictable error rate.
  • The diagram is illustrative, not real Jev data. We could measure a real reliability diagram with our own labeled data later.

  • A fractional score is a position: rank by it, or round to the nearest level if you need one outcome.
  • Different distributions can give the same score: 1.0 could be "all on level 1" or "half on 0, half on 2". Read probabilities and confidence with it.

Noul Probability that a statement is true

Question: "Is the customer asking for a human agent?"  ·  Returns: one number noul from 0 to 1 (probability of yes). No separate confidence.
Input (customer message)noul
Thanks, that fixed it! 0.02
How do I reset my password? 0.07
I need this sorted today, whatever it takes. 0.26
Are you a bot? 0.40
Is there any way to speak to someone about my invoice? 0.84

    "is_human_escalation"].noul > 0.9

if wants_human:
    route_to_agent(ticket)
else:
    route_to_bot(ticket)
  • 0.5 ≠ "medium". It means yes and no are equally likely.
  • One condition per Noul. High value must mean yes.
  • For a degree, use a Score instead.
Source: /primitives/noul
  • Recorded jev-1.13.0 answers. "I need this sorted today" is urgent but never asks for a person: 0.26. "Are you a bot?" hints at wanting a human: 0.40.
  • Threshold by cost of being wrong: 0.5 if both sides equally easy; raise it when a false yes is expensive (refund, paging someone); lower it when missing a true yes is expensive (safety issue). Middle values can go to a person.
  • Docs example on "degree": "Is the candidate strong in Python?" gives 0.81 for a 2-year daily user and 0.92 for an 8-year user, while a 4-level Score gives 2.05 and 2.89: the Score is judged against levels you defined, the Noul is just a probability.
Part 2 · Core concepts

Probabilities vs. confidence

confidence1.00
confidence0.78
confidence0.42
confidence0.20

Four recorded Choice answers from the docs (3, 3, 3 and 4 options).

  • probabilities: what the model believes: the full distribution (sums to 1). Calibration is a claim about these.
  • confidence: one 0–1 number for how peaked that distribution is: a rescaled convenience for thresholds. Example: top probability 0.85 → confidence 0.78.
  • Confidence is not itself calibrated: 0.78 does not mean "78% right". Tune thresholds on your own data (accuracy per confidence bucket).
  • Low confidence: options overlap, or the state says too little.
Our reading (not official). Consistent with every recorded example: (N · p_max − 1) / (N − 1). So it depends on the number of options N, and only on the top probability.
Source: /confidence · /primitives/choice · formula: our fit to the docs' examples
  • Confidence is TypeSafe's own derived statistic, not a standard probability-theory term. Closest standard notion: the ML "classifier confidence" = max predicted class probability. Unrelated to statistical confidence intervals.
  • Docs only state the formula for the 3-option demo: (3 × p_max − 1) / 2. We generalized it and it matches all recorded examples with N = 3, 4, 5. Say "a normalized measure of how peaked the distribution is".
  • Consequences: with two options, p = 0.9 gives confidence 0.8; with three, 0.85. And [0.5, 0.5, 0] and [0.5, 0.25, 0.25] would get the same confidence.
  • "Confidence 0.8" does NOT mean "80% likely correct". Calibration is a claim about the probabilities (e.g. top probability 0.85), not about the derived confidence (0.78). Both numbers are per-answer; calibration is checked across many answers.
  • Why keep confidence? One number per answer on a fixed 0–1 scale regardless of the number of options. For a fixed N it ranks answers the same as the top probability (our inferred formula).

Part 3 · Building with it

AI-powered software: code owns the workflow

Traditional software

A decision tree built from reliable primitives.

LLM agents

The model picks the next step. Every loop is another chance to go off the rails.

AI-powered software

Code owns control flow. The model appears only for narrow, structured judgments.

  1. 1 · Use code when you can. Deterministic rules stay in code.
  2. 2 · Send only relevant state. Less distraction, less context rot.
  3. 3 · Decompose into atomic questions. The docs' "most important concept".
  4. 4 · Ask many questions per request. They run in parallel.
  5. 5 · Combine in code (rules, weighted sums) or feed probabilities to a classical ML model.
  6. 6 · Route on uncertainty. Escalate low confidence to a person or a reasoning model.
Source: /concepts/how-to-build-with-system-one
  • Example of "use code when you can": if days_overdue > 30: route_to_collections(invoice). No model needed.
  • Structured properties the docs list: Structured, Parallel, Comparable, Fast (~100 ms), Calibrated confidence, Self-consistent.
  • Docs' guidance: test thresholds by plotting confidence against accuracy on your data.
  • Step 5 second half: with labeled outcomes, Jev's probabilities can become features for a classical model (AutoResearch cookbook).

0.6 and 0.85 are the docs' example thresholds. Tune them on your own data: plot confidence against accuracy.
Source: /patterns/confidence-routing · /confidence
  • Three paths: high confidence acts automatically; medium proceeds with caution (confirm, review); low does not act (human, clarification, fallback).
  • Checking a balance at 0.6 is fine: worst case the user hears a wrong read-out. Approving a transfer needs much more.
  • "I don't know" as a first-class signal: a system that can't express honest uncertainty can't be trusted.
  • Confidence summarizes distribution concentration, not overall workflow correctness or permission to act. Several acceptable alternatives can also spread probability.

def normalized(answers, qid):
    top_level = len(QUESTIONS[qid].criteria) - 1
    return answers[qid].score / top_level

priority = (0.6 * severity
          + 0.3 * frustration
          + 0.1 * report_quality)
# = 0.6 × 0.62 + 0.3 × 0.64 + 0.1 × 1.0 = «0.664»
  • Scales have different lengths: normalize to 0–1 first.
  • Wrong ranking? Change a weight in code and re-run. No prompt rewrite.
  • Raw scores stay reusable and inspectable.
Source: /primitives/score · /patterns/composite-scoring

  • Weighted sums suit compensating preferences. An "any serious violation" rule needs separate conditions instead.
  • Changing a weight does not require re-running inference if the evidence and question meanings are unchanged.

Wrap-up

Takeaways and discussion

1 · A new contract

State + typed questions in. Typed answers + calibrated probabilities out. No generation, no parsing.

2 · Atomic and composable

Choice, Score, Noul. Many narrow questions per request; code combines them.

3 · Uncertainty is an input

Gate actions by risk with probabilities and confidence: act, confirm, or escalate.

For the discussion

  • Where do we have an LLM "prompt-and-parse" step that is really a typed judgment?
  • Which of our decisions need confidence gating, and what would the thresholds cost us if wrong?
  • How would we validate calibration on our own labeled data before trusting it?
  • Is text-only, English-first good enough for our languages and documents?
